# システム構成図 仕様（作図インプット）

既存の構成図（スライド＋漫画の2系統版）を、**動画生成を加えた3系統版**に更新するための仕様。
1枚もの・横長（16:9 前後）、パネル分割＋色分けフローという既存図の様式を踏襲する。

---

## タイトル

- 主題: **multimodal-article-viewer のシステム構成図**
- 副題: 記事から Google スライド・漫画・解説動画を自動生成し、Firebase 経由で結果をフロントへリアルタイムに返す仕組み

---

## 全体レイアウト

```
┌──── ① フロント ────┐   ┌──── ② 依頼受付 ────┐   ┌──────── ③ バックエンド ────────┐
│  GitHub Pages       │──▶│  Firebase / Slack   │──▶│  article-to-slides-automation  │
│  （静的Webアプリ）   │   │  （依頼キュー）      │   │  （Node.js ワーカー / ローカル）│
│                     │   │                     │   │   共通: 記事本文の取得          │
│                     │   │                     │   │   A. スライド生成の流れ         │
│                     │   │                     │   │   B. 漫画生成の流れ             │
│                     │   │                     │   │   C. 動画生成の流れ  ★新規      │
└─────────────────────┘   └─────────────────────┘   └────────────────┬───────────────┘
         ▲                                                            │ ③ status / url 書き戻し
         │ ④ リアルタイム購読で反映                                    ▼
┌────────┴───────────────────── データ管理（Firebase）─────────────────────────────┐
│  /articles（記事ID）  →  slides / manga / video  それぞれに status・url           │
└──────────────────────────────────────────────────────────────────────────────────┘
┌── 凡例（フローの説明／使用ツールの役割）────────────────────────────────────────┐
└──────────────────────────────────────────────────────────────────────────────────┘
```

既存図から変わる点は3つ。

1. バックエンドのレーンが **A・B の2本から A・B・C の3本**になる（下に伸びる）
2. `/articles` の子が **slides / manga の2つから video を加えた3つ**になる
3. 依頼受付パネルが **Firebase 直接書き込みが主経路**、Slack は併存経路という構成になる

---

## パネル1: フロント（静的Webアプリ）

- パネル見出し: **フロント（静的Webアプリ）／ GitHub Pages**（GitHubアイコン）
- 中の箱: **multimodal-article-viewer**
  - Firebase Auth でログイン
  - 生成依頼フォーム → ボタン3つ: `Googleスライド生成` `漫画生成` `動画生成`
    （※ボタンは各フローの色に合わせる）
  - 記事一覧・結果URL・ステータス表示
  - Firebase `/articles` をリアルタイム購読

---

## パネル2: 依頼受付（リクエスト受付・転送）

**主経路**（太線・実線）

- 箱: **Firebase Realtime Database `/generationRequests`**
  - viewer が1件だけ作成（create-only）
  - `{ text, slides / manga / video, audience, focus, mangaOptions }`
  - `status: queued → processing → done`

**併存経路**（細線・破線、補助的に小さく）

- 箱: **GAS + Slack**（既存の受付経路）
  - Google Apps Script Web App が `requestGeneration` を受信
  - Slack `chat.postMessage` → `[slide-generate]` `[manga-generate]` `[video-generate]`
  - ワーカーの Slack Socket Mode が受け取る

> 作図メモ: 既存図では GAS + Slack が主経路として中央に大きく描かれていたが、現行コードでは
> viewer は Firebase へ直接書き、ワーカーの watcher が `status=queued` を購読して拾う。
> Slack 経路は今も生きているため消さず、**主経路を Firebase、Slack を併存経路**として描き分ける。

---

## パネル3: バックエンド（ワーカー）

- パネル見出し: **バックエンド（ワーカー）／ article-to-slides-automation**
  - 副題: Node.js / TypeScript worker（**ユーザーのローカルPCで常駐**）
- パネル上部に共通の受け口を1行:
  - Firebase `/generationRequests` を購読して依頼を受信

### 共通: 記事本文の取得（3系統の手前に置く横長の箱）

A・B・C の3レーンは**すべてこの箱を通ってから**分岐する。レーンと同じ幅で上部に横たえ、
そこから下に3本の矢印が伸びる形にする。

- 箱の見出し: **content-extractor で記事本文を取得**
- 中に機能を3つ、アイコン付きで横並び（または3行）:

| 機能 | 表示ラベル（1行目 / 2行目） |
|---|---|
| 認証情報の保持 | **ログイン必須サイトに対応** / セッション（Cookie）を保存しておき、会員記事も本文取得 |
| 複数ページの統合 | **ページ送り記事を自動巡回** / 全ページを連結してから1つの記事として要約 |
| 直接入力 | **テキスト直投入にも対応** / URLが無い記事はViewerから本文を貼って生成 |

- 補足1行（小さく）: ・セッションは事前に手動ログインで取得（`npm run session:capture`）。失効時はViewerに再ログインを促す

> 作図メモ: 既存図では「content-extractor で記事本文取得」の1行だけだったが、
> **有料会員記事・連載や長文の分割ページに対応できること**は機能価値が高いので、
> 独立した箱に格上げして3系統の共通土台であることを見せる。
> 巡回の学習（ドメインごとに成功パターンを記憶）まで書くと細かすぎるので、
> 「自動巡回して連結」の粒度で止める。

### レーン A: Googleスライド生成の流れ（青）

```
Codex CLI ──▶ slideData.json ──▶ GAS まじん式レンダラ ──▶ Google スライド
(構成・テキスト生成)   生成          (スライド生成)         / Google Drive に作成
```
- 補足1行: ・必要に応じてチャート画像生成（GASでSVG化 → Playwright でPNG化）

### レーン B: 漫画生成の流れ（緑）

```
Codex CLI ──▶ Step1 / Step2 生成 ──▶ Google Drive ──▶ NotebookLM 操作 ──▶ NotebookLM
(構成・テキスト生成)  Step1: 原作分析・構成設計   へDocs保存    (Playwright / Claude    デックURL取得
                     Step2: 詳細ネーム・コマ割り                  in Chrome)
```
- 補足1行: ・画風A〜G / キャラクターシート画像を参照

> 既存図では NotebookLM 操作が「Claude in Chrome」1つだったが、現在は
> **Playwright 専用ドライバが主経路、Claude in Chrome はフォールバック**。
> 1つの箱に2行で併記するか、箱を重ねて主/副を表現する。

### レーン C: 動画生成の流れ（紫 or オレンジ）★新規

```
Codex CLI ──▶ 構成プラン ──▶ Kokoro TTS ──▶ 字幕タイミング ──▶ HyperFrames ──▶ MP4 を
(構成・図解の生成) 6〜8シーン    (ローカル日本語   実測尺から確定    レンダリング     Google Drive
                  ＋図解        音声合成)                        (ヘッドレスChrome)  に保存
                  ストーリーボード
```
- 補足2行:
  - ・音声の実測時間から尺を55〜65秒へ自動調整（FFmpeg）
  - ・1920x1080 / H.264 の解説動画。すべてローカルで生成（クラウド不使用）

> 作図メモ: A・B と横幅を揃え、箱は5〜6個まで。工程名は上段に太字、括弧書きの補足を下段に小さく
> （既存図の「Codex CLI /（構成・テキスト生成）」と同じ2段組み）。

## パネル4: データ管理（リアルタイム連携）

- パネル見出し: **データ管理（リアルタイム連携）／ Firebase**
- 左側にアイコン2つ: Firebase Auth / Realtime Database
- 中央: **`/articles`（記事ID）** の下に子ノードを3つ横並び

```
┌── slides ──┐  ┌── manga ──┐  ┌── video ──┐
│ status │url│  │ status│url│  │ status│url│   …
└────────────┘  └───────────┘  └───────────┘
```

- 右側に説明2行（アイコン付き）:
  - バックエンドが処理状況と成果物URLを書き戻す
  - フロントが購読してリアルタイム反映

## 矢印（番号付き）

| 番号 | 経路 | ラベル |
|---|---|---|
| ① | フロント → Firebase `/generationRequests` | 生成依頼（slides / manga / video を指定） |
| ② | Firebase → バックエンド | 依頼を購読して受信（`status=queued`） |
| ②' | GAS + Slack → バックエンド（細線・破線） | Slackメッセージ `[slide-generate]` `[manga-generate]` `[video-generate]` |

| ④ | Firebase → フロント | リアルタイム購読で反映 |

## 配色・表現の指針

- パネル背景色は既存図を踏襲: フロント=淡い青、依頼受付=淡いオレンジ、バックエンド=淡い緑、データ管理=淡い紫
- バックエンド内の3レーンは、それぞれのフロー色で細い枠線を付けて区別する（A=青枠、B=緑枠、C=紫枠）
- **動画レーンは新規なので、見出しに小さく「NEW」バッジを付けてもよい**
- ロゴ/アイコンは実在サービスのもの（GitHub, Firebase, Google Slides, Google Drive, Slack, NotebookLM,
  Node.js）を使い、CLI 系（Codex / Claude / HyperFrames / Kokoro）は角丸の枠＋テキストで統一

## 図に入れない方がよいもの

粒度を保つため、以下は**描かない**（詳細は別ドキュメント側で扱う）。

- ジョブディレクトリ構成、チェックポイント、再開の仕組み
- リトライ・フォールバックの分岐（rich→basic など）※ NotebookLM の主/副だけは例外的に併記
- 直列キュー・セマフォなどの排他制御
- フィーチャーフラグ（`VIDEO_GENERATION_ENABLED` など）
- エラー種別・`action_required` の状態遷移
- `/articleSources` `/artifactDiagnostics` `/sessionStatus` などの補助パス
- 記事取得の内部詳細（ドメイン別のページ送りパターン学習、Cookie の保存場所や有効期限の推定、
  X/YouTube など個別サイトの取得経路）。「ログイン保持」「複数ページ巡回」の2機能名までに留める

## 要確認（作図前に確定したい点）

1. viewer が現在も GAS + Slack 経路を使っているか、Firebase 直接書き込みに一本化済みか。
   一本化済みなら、②' の Slack 経路は凡例の注記程度まで小さくしてよい。
2. 動画フローの色。既存2色（青・緑）と識別しやすいのは紫だが、Firebase のデータフローが
   既に紫のため、オレンジ系にするか、データフローの色を変えるかの判断が必要。
